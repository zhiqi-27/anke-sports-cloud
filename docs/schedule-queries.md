# 赛程查询与链接批量读取

HTTP 与 MCP 继续共用 `actions.get_schedule`，接口和 OpenAPI 不变。原实现先为整个查询结果逐场读取链接、渲染描述，再截取一页；活动窗口两万场时，即使返回100场也会发出约两万条SQL。

现在先在数据库按日期缩小候选范围，读取分页与匹配需要的字段；只有最终页的比赛加载完整内容和链接。非关注查询不读取候选比赛的参与方JSON，无搜索词时也不读取候选标题。个人关注集合每次查询编译一次。仍对完整匹配集合计算游标摘要，保留后续页变化、账号版本和查询条件变化时的失效行为；这一步仍与窗口内候选数量相关，没有宣称任意数据规模下恒定开销。

`starts_at` 可以带不同时区偏移，所以SQL日期边界使用保守范围，随后按真实时间执行 `[from,to)` 判断和排序。修复了直接按ISO字符串排序造成的先后颠倒；事件身份、原始时间字段和时区未改变。仅日期占位继续使用已有的日期筛选语义，不伪造开赛时间。接近datetime最小/最大年份的边界也不会因扩大候选范围而溢出。

分页后再次读取的比赛若已改版或被删除，返回 `CURSOR_EXPIRED`，不把旧分页绑定与新比赛内容混在一起。此检查不能代替数据库事务隔离；真实MySQL并发仍需验收。

链接只在本次请求内按事件批量加载，SQL先限定 `public` 和当前账号，再应用原有屏蔽、固定、创作者范围、地区与审核发布规则。公共审核记录也批量读取；不会把草稿视为公开入口。没有增加跨账号缓存。每批最多400个事件ID/审核ID，避免大Feed产生无限长的SQL参数列表。

个人和公共Feed发布复用该批量读取路径，并先在SQL排除日期窗口之外的旧赛季。UID、描述选择、投影版本、历史保留和相同内容不更新ETag的规则保持不变。Feed请求仍只读已发布快照。

## 复现本地容量场景

```sh
uv run python -m experiments.schedule_capacity --samples 20 --concurrency 1 --output evidence/capacity-serial-new.json
uv run python -m experiments.schedule_capacity --samples 20 --concurrency 4 --output evidence/capacity-concurrent-new.json
```

脚本建立独立临时SQLite和真实loopback HTTP服务：20,000场活动比赛、20,000场旧比赛、1,000个账号、200个创作者与10,000条私人链接，全部合成。运行结束关闭服务和临时库；不连接主库、不调用上游、不记录令牌或私人Feed路径。启动前拒绝云环境，输出文件不能覆盖已有证据。

该场景存储1,000个账号，实际最大4个并发请求；只发布一个含200场比赛的Feed。赛程测量使用100场一页，先预热HTTP/数据库路径，没有应用结果缓存。它不能证明1,000用户同时在线、所有Feed发布、通知到Feed的两分钟目标或真实MySQL/Azure性能。

当前结果和边界：[容量实测记录](../evidence/schedule-queries-2026-09-10.md)。回归测试 `tests/test_schedule_queries.py` 覆盖时区排序/边界、字面搜索、分页加载上限、关注与版本失效、公开审核/私人链接，以及独立SQLite连接的改期竞争。
